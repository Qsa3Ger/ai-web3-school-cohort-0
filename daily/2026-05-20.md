    10|## RAG — 检索增强生成
    11|
    12|### 核心理念
    13|RAG 不是"给模型接一个向量库"这么简单。它是一条把**外部知识**取回、筛选、引用、交给模型使用的**证据链**。
    14|
    15|**目的：** 解决 LLM 训练数据过期、context window 有限的问题。
    16|
    17|### 为什么重要
    18|LLM 的训练知识会过期，也放不下整个互联网。RAG 的作用：
    19|- 用户提问 → 系统先从知识库找相关材料 → 模型基于材料回答
    20|
    21|常见应用：产品文档问答、代码库助手、研究摘要、客服知识库、SDK Copilot、内部知识检索。
    22|
    23|**关键认知：** 没有 citation 和 freshness 的 RAG，只是把幻觉从模型内部搬到了检索系统里。
    24|
    25|### 第一性原理
    26|1. **RAG 的可靠性取决于证据链，不取决于向量库**
    27|2. **检索结果不是事实**：只是候选证据，仍要看来源、时间、版本
    28|3. **引用要能回到原文**：答案里的关键判断应追溯到具体文档
    29|4. **检索失败要允许拒答**：找不到证据时应说"不确定"
    30|
    31|### 知识节点
    32|
    33|| 概念 | 一句话 | 关键点 |
    34||------|--------|--------|
    35|| **Chunking** | 切文档成可检索片段 | 按结构切（标题、API endpoint、函数说明），保留 metadata（来源、版本、时间） |
    36|| **Vector DB** | 存 embedding + metadata 并检索 | 向量相似 ≠ 答案正确；先过滤再排序 |
    37|| **Retriever** | 取回候选材料 | 不只看语义相似度，还要考虑版本、时间、环境 |
    38|| **Rerank** | 对候选结果重新排序 | 减少"标题相似但内容不对"的结果 |
    39|| **Citation** | 连接答案和来源 | 让用户能验证答案的来源和可靠性 |
    40|
    41|### RAG 在 AI × Web3 中的位置
    42|RAG 位于 Knowledge Base 和模型之间。帮 Agent：
    43|- 查资料、补上下文、引用证据
    44|- 但不负责最终执行
    45|
    46|**重要安全边界：** 当 RAG 结果要影响链上动作时，还需要接 simulation、policy 和 human check。文档说某函数"可以调用"，不等于当前用户"应该签名"。
    47|
    48|### 最小实践
    49|做一个"协议文档 RAG 问答"的最小版本：
    50|1. 选择一个官方文档站
    51|2. 抓取 10-20 篇页面，按标题结构切 chunk
    52|3. 存入向量库
    53|4. 用户提问 → 返回答案 + 引用
    54|
    55|至少测试三类问题：
    56|- ✅ 文档中明确存在的 API 用法
    57|- ✅ 文档中不存在的问题（应拒答）
    58|- ✅ 旧版本或不确定版本的问题（应提示核对版本）
    59|
    60|输出格式：区分 answer / source / uncertainties / needs_version_check

    64|## Agent（智能体）
    65|
    66|### 核心理念
    67|Agent 是能围绕目标持续调用工具、读取状态、调整步骤的 AI 系统。
    68|**关键：** 不在于"像人"，而在于在明确权限和可审计流程里，把建议推进到行动。
    69|
    70|### Agent vs LLM 的区别
    71|| | LLM | Agent |
    72||--|-----|-------|
    73|| 做什么 | 回答问题、生成文本 | 拆任务、调API、写代码、执行操作 |
    74|| 风险 | 答错 | 做错（可能造成实际损失） |
    75|| 输出 | 文本 | 行动 + 文本 |
    76|
    77|### 第一性原理
    78|1. **Agent 不是自主权，而是被约束的执行循环**
    79|2. **工具比回答更危险：** 读数据、写数据库、发请求、改配置不是同一风险等级
    80|3. **状态必须外置可查：** 任务进度、工具结果、失败原因、用户确认都要记录
    81|4. **停止条件要明确：** 达到目标、超出预算、信息不足、风险越界、用户拒绝都应停止
    82|
    83|### 知识节点
    84|
    85|| 概念 | 一句话 | 关键点 |
    86||------|--------|--------|
    87|| **Tool Use** | 调用工具从"会回答"到"能做事" | 工具设计要明确：输入schema、权限范围、是否只读、有无副作用 |
    88|| **Planning** | 把目标拆成步骤 | 计划只是候选路线，不是授权。越靠近高风险动作越需要系统拆开检查 |
    89|| **State** | Agent 当前任务状态 | 不能只放在 prompt 历史，要可查询、可恢复、可审计 |
    90|| **Reflection** | Agent 检查自己中间结果并修正 | 只能辅助诊断，不能作为最终安全判断 |
    91|| **Multi-Agent** | 多个 Agent 分工协作 | 先问：多个 Agent 是否真的减少复杂度？ |
    92|
    93|### Agent 在 AI × Web3 中的位置
    94|Agent 位于模型能力和链上执行之间。一个安全的 AI × Web3 Agent 架构：
    95|
    96|```
    97|用户提出目标 → Agent 生成计划 → 系统拆成只读/写入步骤
    98|    → 只读自动执行 → 写入进 policy 检查
    99|    → Simulation 展示链上影响 → 用户确认高风险动作
   100|    → Wallet 执行 → 日志记录所有步骤
   101|```
   102|
   103|**最危险的设计：** 让 Agent 同时拥有模糊目标、广泛工具、长期记忆和大额资产权限。
   104|
   105|### 最小实践
   106|做一个"DAO 提案研究 Agent"的最小版本：
   107|- 只读动作：读取提案、检索讨论、总结正反观点、标记缺失信息
   108|- 输出：投票前检查清单
   109|- 不要在输出前进行任何实际投票操作
   110|- 需要用户明确授权 + Simulation 后才能生成投票交易草稿
